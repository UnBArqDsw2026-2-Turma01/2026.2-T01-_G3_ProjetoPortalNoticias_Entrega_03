    Participantes no Foco_01

    Nome do Membro Lições Aprendidas Uso da IA Generativa (SENSO CRÍTICO)
    Andre Henrique de Souza Belarmino Aprendi que o Abstract Factory serve para criar famílias de objetos relacionados por meio de uma única interface, sem que o cliente conheça as classes concretas. Diferente do Factory Method, que escolhe a classe de um único produto, ele garante que todas as peças criadas pertençam à mesma família. Entendi também o equilíbrio do padrão: acrescentar uma nova família é fácil e não afeta o cliente, mas acrescentar um novo tipo de produto obriga a alterar a fábrica abstrata e todas as fábricas concretas. Por fim, percebi que os produtos abstratos devem definir comportamento, para que cada família implemente esse comportamento do seu jeito. Usei o Claude Sonnet 5 para gerar o primeiro diagrama. Comparando com os slides, encontrei erros: o cliente não usava os produtos abstratos, os produtos não tinham comportamento e faltava a classe ConfiguracaoComunidade. Usei o diagrama apenas como rascunho para montar o meu. Na implementação, usei o Claude Code com o MCP do Figma para trazer as imagens do protótipo e revisar o código. A IA ajuda a começar, mas erra com confiança, então tudo precisa ser conferido.
    Giovanna Felipe Guimaraes Aprendi que o Singleton resolve um problema bem concreto do portal: várias telas dependem dos mesmos dados, e ter um único repositório evita cópias inconsistentes. Na implementação, percebi que o JavaScript não tem construtor privado, então precisei criar um mecanismo próprio (o atributo estático #liberado) para impedir o new fora do getInstancia(). Também ficou mais clara para mim a diferença entre composição e agregação, e como dois padrões criacionais podem trabalhar juntos: o Builder monta a notícia e o Singleton guarda. Por outro lado, entendi que o Singleton funciona como um estado global e deve ser usado com cuidado, só quando realmente precisa existir uma única instância. Usei o Gemini para gerar uma primeira versão do diagrama de classes. Ele acertou a estrutura básica do Singleton, mas analisando com calma encontrei erros: usou composição entre o repositório e a notícia (sendo que quem cria a notícia é o Builder), não previu nenhum método de publicação, usou associação onde deveria ser dependência e misturou nomes como getInstance e obterInstancia. Por isso não usei o diagrama dele como resposta final, e sim como ponto de partida para montar o meu. A IA ajuda a começar rápido, mas o resultado precisa ser conferido com o conteúdo das aulas e com o contexto real do projeto.
    Joao Pedro Lopes da Cruz Aprendi que o builder é a escolha ideal quando não se sabe como será a estrutura final do objeto, no caso do projeto da notícia, uma vez que os blocos de texto, imagens, mídia, etc podem aparecer em diferentes ordens. Assim, o builder se apresentou como a solução ideal por construir a página da notícia conforme solicitado pelo usuário, através da orquestração do builder O uso de IA é descrito em detalhes no texto, mas no geral a IA foi usada para melhorar o texto escrito (sempre passando por revisão final humana) e geração de diagramas para o ponto de partida (no decorrer da página coloquei minhas considerações quanto a qualidade dos diagramas gerados). Além disso, a IA auxiliou na implementação do código através do MCP com o figma, que reaproveita o protótipo navegável transformando-o automaticamente em código HTML e CSS. Foi usado o Gemini pro 3.1 (diagrama), claude Sonnet 5.5 (diagrama) e o claude opus 5.5 (aproveitamento do protótipo navegável)

    Contexto (Problema)

    1. Builder de notícias - João Pedro Lopes da Cruz

    Pensando na funcionalidade de criar uma notícia pensei que poderia haver templatezinho de estrutura de como ficaria a página da notícia, alguns com a imagem em destaque grande, outro com apenas uma imagem pequena ao lado do texto e uma notícia que comporte um carrossel de imagens. Pensando nessas estruturas pré definidas optei por implementar a geração da página usando um builder, pois todas as notícias seguirão a mesma estrutura base de informações (mídias, texto, título, categoria, autor, etc).

    2. Singleton do Repositório de Notícias - Giovanna Felipe Guimaraes

    No portal, várias telas dependem das mesmas notícias publicadas: a página inicial mostra as mais recentes, a página de categoria filtra por assunto e a área de destaques puxa as principais. Se cada uma dessas telas criasse o seu próprio repositório de notícias, cada uma teria a sua própria cópia dos dados. Assim, uma notícia publicada poderia aparecer na home e não aparecer na categoria, ou aparecer duplicada, além de abrir várias "conexões" para buscar a mesma informação sem necessidade. Por isso escolhi o Singleton para o repositório de notícias: ele garante que exista uma única instância guardando as notícias publicadas e oferece um ponto de acesso global a ela. Com isso, toda tela que chama o repositório recebe o mesmo objeto, e o que é publicado num lugar aparece igual em todos os outros. Ele também se conecta ao Builder do João, porque a notícia que o Builder monta é publicada nesse repositório único.

    3. Abstract Factory de Comunidades - André Henrique de Souza Belarmino

    Na Entrega 2, o diagrama de classes que modelei tratava Comunidade como uma especialização de Tag, com os atributos corTema e regrasModeracao e o método atualizarDados(). Só que, olhando de novo para esse modelo com a lente de Padrões de Projeto, percebi um problema: criar uma nova comunidade não deveria significar simplesmente preencher esses dois campos de texto livre. Comunidades de categorias diferentes (ex: uma comunidade técnica, no estilo dev.to, e uma comunidade de eventos) precisam nascer com um conjunto coerente de configurações, um tema visual que combine com o propósito da comunidade, uma política de moderação com o rigor adequado ao tipo de conteúdo, e um widget de destaque relevante para aquele público. Se isso for feito com um amontoado de if/else checando a categoria toda vez que uma comunidade for criada, é fácil alguém acabar misturando peças incompatíveis (ex: tema de comunidade técnica com política de moderação pensada para eventos).

    Esse é exatamente o problema que o Abstract Factory resolve: ele define uma interface para criar famílias de objetos relacionados sem o cliente precisar conhecer as classes concretas, garantindo que os produtos de uma mesma família sejam sempre usados em conjunto. Por isso escolhi aplicá-lo à criação de comunidades, retomando e aprofundando o meu próprio recorte da Entrega 2.

    2. Singleton do Repositório de Notícias

    Para começar a modelagem, pedi ao Gemini um diagrama de classes do Singleton aplicado ao repositório de notícias, acessado pela página inicial, pela página de categoria e pelos destaques.

    Diagrama GoF criacional: Gemini - prompt por Giovanna Felipe Guimaraes

    A IA acertou o básico do Singleton (construtor privado, atributo estático com a instância única e um método de acesso global), mas encontrei alguns problemas. Ela ligou o repositório à Noticia por composição, como se o repositório fosse dono do ciclo de vida das notícias, sendo que a notícia é criada antes, pelo Builder, e só depois é guardada.     3. Abstract Factory de Comunidades

    Para ter um ponto de partida, pedi ao Claude Sonnet 5 um diagrama inicial, descrevendo o cenário (famílias de tema visual, política de moderação e widget padrão por categoria de comunidade) e pedindo que a estrutura seguisse à risca os papéis clássicos do Abstract Factory (AbstractFactory, ConcreteFactory, AbstractProduct, ConcreteProduct, Client).

    Diagrama GoF criacional: Claude Sonnet 5 - prompt por André Henrique de Souza Belarmino

    O diagrama modela duas famílias concretas (Tecnologia e Eventos) para manter o exemplo enxuto, mas a estrutura permite acrescentar novas famílias (ex: Bem-estar) sem alterar o cliente CriadorDeComunidade — basta criar uma nova ConcreteFactory e seus três ConcreteProducts correspondentes. Os três produtos abstratos (TemaVisual, PoliticaModeracao, WidgetPadrao) foram modelados como interfaces, e não como atributos soltos em Comunidade, justamente para impedir que o código cliente misture peças de famílias diferentes. O CriadorDeComunidade é o cliente do padrão: ele recebe uma fábrica concreta (injetada conforme a categoria escolhida ao criar a comunidade) e usa exclusivamente a interface ComunidadeFactory, sem conhecer ComunidadeTecnologiaFactory ou ComunidadeEventosFactory diretamente. O resultado desse processo (ConfiguracaoComunidade) é o que acaba populando os atributos corTema e regrasModeracao já existentes na classe Comunidade da Entrega 2.

    Comparando o diagrama da IA com os slides da aula de GoFs Criacionais, encontrei pontos que precisavam ser corrigidos:

    • O cliente não conhecia os produtos abstratos. Pela modelagem genérica do padrão, o Client usa as interfaces declaradas tanto em AbstractFactory quanto em AbstractProduct. No diagrama da IA, CriadorDeComunidade só se relacionava com ComunidadeFactory, faltando as associações com TemaVisual, PoliticaModeracao e WidgetPadrao.
    • Os produtos abstratos eram interfaces com atributos e sem comportamento. Uma interface UML não deveria ter atributos privados, e nos exemplos da aula os produtos têm comportamento (paint(), calculateTaxes()). Transformei ComunidadeFactory e os três produtos em classes abstratas (como a aula indica: "o normal é ser Classe Abstrata") e dei a cada produto um método: aplicar(), moderar() e renderizar().
    • Não ficava claro onde a fábrica concreta era escolhida. A IA apenas citou que a fábrica seria "injetada conforme a categoria". Seguindo o defineFactory() do exemplo GUIFactory da aula, acrescentei o método estático definirFactory(categoria), que é chamado a partir da área de criação de comunidade: o usuário escolhe a categoria e o método devolve a fábrica concreta correspondente.
    • O texto da IA citava uma classe que não aparece no diagrama. O ConfiguracaoComunidade retornado por montarConfiguracao() não estava no modelo. Acrescentei essa classe, ligando-a à Comunidade da Entrega 2, cujos atributos corTema e regrasModeracao ela preenche.

    Também considerei permitir uma comunidade "personalizada", em que o usuário escolhesse cada peça livremente. Desisti porque isso vai contra o objetivo do padrão, que é criar famílias de objetos relacionados: se cada peça pode vir de uma família diferente, a fábrica deixa de garantir a coerência. Em vez disso, mostrei a principal vantagem do padrão acrescentando duas famílias fixas, Cultura e Política, sem precisar alterar o cliente CriadorDeComunidade.

    1. A interface do Builder (js/builders.js)

    O JavaScript não tem interface como o Java, então criei a NoticiaBuilder como uma classe que não pode ser instanciada diretamente (o construtor verifica new.target) e cujos métodos lançam erro se não forem sobrescritos.     2. Os builders concretos: mesmos passos, visuais diferentes

    Os três builders recebem exatamente as mesmas chamadas, mas cada um decide como configurar cada parte da notícia. O NoticiaDestaqueBuilder coloca a capa grande ocupando toda a largura, aplica a letra capitular no primeiro parágrafo e mostra as imagens em largura total. O NoticiaCompactaBuilder usa uma capa em miniatura e coloca as imagens menores ao lado do texto. Comparando o mesmo método nos dois, dá para ver a diferença:

// NoticiaCompactaBuilder
adicionarTexto(texto) {
  this.noticia.adicionar(new TextoBloco(texto));

    3. O Director e o roteiro do redator (js/director.js)

    Essa é a parte central do por quê o builder foi usado, os blocos de uma notícia aparecem na ordem que o redator escolheu, então o Director recebe essa ordem como um roteiro, uma lista de itens, em que cada item tem um tipo (TEXTO, IMAGEM, CARROSSEL ou TOPICOS) e o seu conteúdo. O construirPersonalizada() monta primeiro o cabeçalho e depois percorre o roteiro chamando o passo correspondente do builder. O Director só conhece a interface NoticiaBuilder, então ele não sabe (e não precisa saber) qual builder concreto está usando.

    construirPersonalizada(titulo, subtitulo, categoria, capa, autor, roteiro, fonte) {
  this.validar(roteiro);

  this.builder.reset();
  this.builder.definirCabecalho(titulo, categoria, capa);
  if (subtitulo) {
    this.builder.definirSubtitulo(subtitulo);
  }
  this.builder.definirAutor(autor);

  for (const item of roteiro) {
    switch (item.tipo) {
      case TipoBloco.TEXTO:
        this.builder.adicionarTexto(item.conteudo);
        break;
      case TipoBloco.IMAGEM:
        this.builder.adicionarImagem(item.conteudo);
        break;
      case TipoBloco.CARROSSEL:
        this.builder.adicionarCarrossel(item.conteudo);
        break;
      case TipoBloco.TOPICOS:
        this.builder.adicionarTopicos(item.conteudo);
        break;
    }
  }

  if (fonte) {
    this.builder.definirRodape(fonte);
  }
}

    Antes de chamar qualquer passo, o método privado validar() confere o roteiro: ele não pode estar vazio, um texto não pode estar em branco, uma imagem precisa de URL, o carrossel precisa de pelo menos 2 imagens e a lista de tópicos não pode estar vazia. Se algo estiver errado, o Director recusa o roteiro e informa qual bloco tem problema. Na página "Montar notícia", essa mensagem aparece para o redator na etapa de revisão. O Director também oferece o construirNoticiaPadrao(), uma receita fixa para notícias simples (cabeçalho, autor e um único texto).

    1. A instância única e o construtor bloqueado (js/repositorioNoticias.js)

    Como o JavaScript não oferece construtores privados, como ocorre em Java, utilizei um atributo estático privado (#liberado) como mecanismo de controle: o construtor só pode ser executado quando a chamada parte do próprio getInstancia(). Qualquer tentativa externa de instanciar a classe com new RepositorioNoticias() lança uma exceção.

  #noticias = [];

  constructor() {
    if (!RepositorioNoticias.#liberado) {
      throw new Error("RepositorioNoticias é um Singleton: use RepositorioNoticias.getInstancia() em vez de new.");
    }
    ...
  }

    2. O ponto global de acesso

    O método estático getInstancia() cria o repositório apenas no momento da primeira solicitação (lazy initialization) e, nas chamadas seguintes, retorna sempre a mesma instância. O bloco try/finally assegura que o mecanismo de controle seja restaurado mesmo que ocorra alguma falha durante a criação do objeto.

      static getInstancia() {
    if (RepositorioNoticias.#instancia === null) {
      RepositorioNoticias.#liberado = true;
      try {
        RepositorioNoticias.#instancia = new RepositorioNoticias();
      } finally {
        RepositorioNoticias.#liberado = false;
      }
    }
    return RepositorioNoticias.#instancia;
  }

    3. Os dados que o Singleton protege

    A lista de notícias é encapsulada em um atributo privado (#noticias). O método publicar() impede o cadastro de notícias duplicadas, e os métodos de consulta retornam novas listas, de modo que nenhuma tela consegue alterar o estado interno do repositório. Os destaques correspondem às notícias construídas pelo NoticiaDestaqueBuilder.

      publicar(noticia) {
    if (this.#noticias.some((n) => n.titulo === noticia.titulo)) {
      return false;
    }
    this.#noticias.push(noticia);
    return true;
  }

  listarPorCategoria(categoria) {
    return this.#noticias.filter((n) => n.categoria === categoria).reverse();
  }

  listarDestaques() {
    return this.#noticias.filter((n) => n.variante === "destaque").reverse();
  }

    3. Abstract Factory de Comunidades

    O código está em demonstracao_codigos/SubGrupo1/abstract-factory. A implementação foi feita em JavaScript puro e roda direto no navegador, sem instalar nada: basta abrir o arquivo index.html.

    • Página da comunidade (index.html): reproduz a página de comunidade do protótipo no Figma, com banner, ícone, widget de destaque, últimas notícias e o formulário de publicação. No painel do canto inferior, é possível escolher uma comunidade de exemplo e trocar a fábrica concreta (Tecnologia, Esportes, Cultura ou Política). Ao trocar a fábrica, o tema, o widget e a regra de moderação mudam todos juntos, e o painel "Passos chamados na fábrica" mostra quais produtos foram criados.

    Cada participante do padrão ficou em um arquivo separado dentro de js/, para ficar fácil relacionar o código com o diagrama:

    Participante do padrão Classe(s) Arquivo
    AbstractFactory ComunidadeFactory fabricas.js
    ConcreteFactory ComunidadeTecnologiaFactory, ComunidadeEsportesFactory, ComunidadeCulturaFactory, ComunidadePoliticaFactory fabricas.js

    1. A fábrica abstrata (js/fabricas.js)

    O JavaScript não tem classes abstratas, então a ComunidadeFactory verifica new.target no construtor para não ser instanciada diretamente, e seus métodos de criação lançam erro se não forem sobrescritos. Seguindo o defineFactory() do exemplo GUIFactory da aula, ela também tem o método estático definirFactory(categoria), que recebe a categoria escolhida na criação da comunidade e devolve a fábrica concreta correspondente. No lugar de um if/else, usei um mapa de categorias, como sugere a observação do slide sobre melhorar essa comparação.

    class ComunidadeFactory {
  constructor() {
    if (new.target === ComunidadeFactory) {
      throw new Error("ComunidadeFactory é uma interface: use uma das fábricas concretas.");
    }
  }

  static definirFactory(categoria) {
    const fabricas = {
      tecnologia: ComunidadeTecnologiaFactory,
      esportes: ComunidadeEsportesFactory,
      cultura: ComunidadeCulturaFactory,
      politica: ComunidadePoliticaFactory,
    };
    const Fabrica = fabricas[categoria];
    if (!Fabrica) {
      throw new Error(`Categoria de comunidade desconhecida: ${categoria}`);
    }
    return new Fabrica();
  }

  criarTema() { throw new Error("criarTema() não implementado"); }
  criarPoliticaModeracao() { throw new Error("criarPoliticaModeracao() não implementado"); }
  criarWidgetPadrao() { throw new Error("criarWidgetPadrao() não implementado"); }
}

    2. As fábricas concretas: uma por família

    Cada fábrica concreta sobrescreve os três métodos de criação e devolve somente produtos da sua família. É isso que garante que uma comunidade de esportes nunca receba, por exemplo, a moderação de política.

    class ComunidadeEsportesFactory extends ComunidadeFactory {
  criarTema() { return new TemaEsportes(); }
  criarPoliticaModeracao() { return new PoliticaModeracaoEsportes(); }
  criarWidgetPadrao() { return new WidgetPlacarAoVivo(); }
}

class ComunidadePoliticaFactory extends ComunidadeFactory {
  criarTema() { return new TemaPolitica(); }
  criarPoliticaModeracao() { return new PoliticaModeracaoPolitica(); }
  criarWidgetPadrao() { return new WidgetPautaPolitica(); }
}

    4. Os produtos concretos: o mesmo método, regras diferentes

    Na política de moderação fica mais visível o polimorfismo: o cliente sempre chama moderar(), mas cada família implementa uma regra própria. Em Esportes, um post que fala de resultado precisa ter o placar e ofensas são recusadas. Em Política, toda afirmação precisa indicar a fonte e o autor.

    class PoliticaModeracaoEsportes extends PoliticaModeracao {
  moderar(conteudo) {
    const ofensivo = /\b(lixo|vagabundo|idiota)\b/i.test(conteudo);
    const citaResultado = /\b(venceu|perdeu|empatou|resultado)\b/i.test(conteudo);
    const temPlacar = /\b\d+\s*[x×-]\s*\d+\b/.test(conteudo);
    return !ofensivo && (!citaResultado || temPlacar);
  }
}

class PoliticaModeracaoPolitica extends PoliticaModeracao {
  moderar(conteudo) {
    return /fonte:/i.test(conteudo) && /autor:/i.test(conteudo);
  }
}

    5. O Cliente (js/criador.js)

    O CriadorDeComunidade recebe uma fábrica no construtor e usa apenas a interface da ComunidadeFactory e dos produtos abstratos. Ele não cita nenhuma classe concreta, por isso funciona com qualquer família, e acrescentar uma família nova não exige alterar este código. O resultado é uma ConfiguracaoComunidade, que reúne as três peças criadas.

    class CriadorDeComunidade {
  constructor(factory) {
    this.factory = factory;
    this.passos = [];
  }

  montarConfiguracao(nome, descricao) {
    this.passos = [];
    const tema = this.chamar("criarTema", () => this.factory.criarTema());

    this.garantirMesmaFamilia(tema, moderacao, widget);
    return new ConfiguracaoComunidade(nome, descricao, tema, moderacao, widget);
