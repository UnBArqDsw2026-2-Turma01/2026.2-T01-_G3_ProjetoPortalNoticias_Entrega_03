### GoF Estrutural - Matheus Eiki Kimura
#### Contexto (Problema)
??? note "Contexto (problema)"
    O site de notícias UGC permite que usuários criem publicações dentro de comunidades, e toda publicação passa pela moderação antes de ser exibida. Quando o moderador aprova ou reprova um post, o sistema precisa avisar pessoas diferentes pela web: o autor, nos dois casos, e os seguidores da comunidade, quando o post é aprovado.

    Sem um padrão, a solução mais direta seria o ModeracaoService chamar diretamente a lógica de notificação logo após aprovar ou reprovar. Isso gera três problemas:

    Acoplamento forte. A moderação passa a conhecer repositórios de seguidores, o canal web e as regras de cada mensagem. Qualquer mudança nas notificações exige alterar o módulo de moderação.
    Violação do princípio aberto/fechado. Cada novo interessado no evento (por exemplo, um futuro ranking de autores ou um e-mail) obriga a editar o código da moderação, que vira uma cadeia crescente de if e chamadas.
    Falhas em cascata. Se o envio de uma notificação falhar, a própria operação de moderar poderia falhar junto, mesmo sendo apenas um efeito colateral.

    O problema central é que um objeto (a moderação) muda de estado e vários outros objetos precisam reagir a isso, sem que o primeiro saiba quem são eles nem quantos são. Esse é exatamente o problema que o padrão Observer resolve: a moderação publica um evento no EventBus (Subject) e os handlers inscritos (Observers) reagem de forma independente.

    Com o Observer, cada tipo de aviso passou a ter seu próprio handler: avisar os seguidores sobre um novo post, avisar o autor da aprovação e avisar o autor da reprovação. Todos executam a mesma sequência de passos: descobrir quem deve receber, montar a mensagem, salvar a notificação e enviá-la ao navegador do usuário.

    Se cada handler implementasse essa sequência por conta própria, o código de persistência e envio ficaria duplicado em três lugares. Pior, a ordem dos passos poderia divergir entre eles: um handler poderia enviar ao navegador antes de salvar, outro poderia esquecer de remover destinatários repetidos. A cada novo tipo de notificação, essa duplicação e o risco de inconsistência cresceriam.

    O que realmente muda entre os handlers são apenas dois passos: quem recebe e qual é o conteúdo. O restante é idêntico. O problema, portanto, é definir o esqueleto fixo de um algoritmo e permitir que subclasses variem somente partes específicas dele, sem alterar a estrutura geral. É isso que o Template Method resolve: NotificationHandler.handle() fixa a ordem dos passos, enquanto resolveRecipients() e buildMessage() ficam como operações abstratas implementadas por cada handler concreto.

    **Trecho 1 · `EventHandler` — a interface Observer**<br>
    Arquivo: `src/modules/notifications/application/EventHandler.ts` — caixa do diagrama: **"EventHandler — Observer: handle(evento)"**.

    ```typescript
    import type { DomainEvent } from "../domain/events/DomainEvent";

    /**
     * GoF Observer — papel "Observer".
     * Quem quiser reagir a um evento implementa esta interface.
     */
    export interface EventHandler<E extends DomainEvent = DomainEvent> {
      readonly eventType: E["type"];
      handle(event: E): Promise<void>;
    }
    ```

    **Explicação:** essa interface é o começo de tudo. Ela só pede duas coisas de quem quiser participar: dizer em qual evento quer escutar (o `eventType`) e aceitar a chamada de `handle(evento)` quando esse evento acontecer. É a caixa roxa do diagrama, e todas aquelas setas tracejadas de "implementa" chegam exatamente nela.

    **Trecho 2 · `EventBus` — o Subject**<br>
    Arquivo: `src/modules/notifications/application/EventBus.ts` — caixa do diagrama: **"EventBus — Subject: publish, subscribe"**.

    ```typescript
    export class EventBus {
      private readonly handlers = new Map<string, EventHandler<any>[]>();

      subscribe<E extends DomainEvent>(handler: EventHandler<E>): () => void {
        const list = this.handlers.get(handler.eventType) ?? [];
        list.push(handler);
        this.handlers.set(handler.eventType, list);
        return () => this.unsubscribe(handler);
      }

      unsubscribe<E extends DomainEvent>(handler: EventHandler<E>): void {
        const list = this.handlers.get(handler.eventType) ?? [];
        this.handlers.set(
          handler.eventType,
          list.filter((h) => h !== handler),
        );
      }

      /**
       * Notifica todos os observers do tipo do evento.
       * allSettled: se um handler falhar, os demais ainda rodam e
       * a moderação (quem publicou) não é afetada.
       */
      async publish(event: DomainEvent): Promise<void> {
        const list = this.handlers.get(event.type) ?? [];
        const results = await Promise.allSettled(list.map((h) => h.handle(event)));
        results.forEach((r, i) => {
          if (r.status === "rejected") {
            console.error(
              `[EventBus] handler #${i} falhou para ${event.type}:`,
              r.reason,
            );
          }
        });
      }
    }
    ```

    **Explicação:** o `handlers` é um `Map` que guarda, para cada tipo de evento, a lista de quem quer ser avisado — esse é o Subject do diagrama. Quem se inscreve via `subscribe()` entra nessa lista e ainda recebe de volta uma função para cancelar a inscrição depois, se precisar. Quando chega um `publish()`, o bus procura a lista daquele evento e chama o `handle()` de cada um — essa chamada é a flecha sólida que sai da caixa EventBus no desenho. Só um detalhe bem prático: o `publish()` usa `Promise.allSettled` em vez de `Promise.all`, justamente para que a falha de um handler não pare os outros nem atrapalhe a moderação, que é quem publicou.

    **Trecho 3 · `NotificationHandler` — a classe abstrata do Template Method**<br>
    Arquivo: `src/modules/notifications/application/NotificationHandler.ts` — caixa do diagrama: **"NotificationHandler — handle(evento) / # resolverDestinatarios() / # montarMensagem() / persistirEEnviar()"**.

    ```typescript
    /**
     * GoF Template Method — papel "AbstractClass".
     * handle() define a ORDEM dos passos (o template):
     *   1. resolveRecipients  (abstrato → varia por handler)
     *   2. buildMessage       (abstrato → varia por handler)
     *   3. persistAndSend     (concreto → igual para todos)
     *
     * Também é um "Observer" concreto: implementa EventHandler.
     * Subclasses NÃO devem sobrescrever handle().
     */
    export abstract class NotificationHandler<E extends DomainEvent>
      implements EventHandler<E>
    {
      abstract readonly eventType: E["type"];

      constructor(
        private readonly notifications: NotificationRepository,
        private readonly channel: WebChannel,
      ) {}

      /** Template method. */
      async handle(event: E): Promise<void> {
        const recipientIds = await this.resolveRecipients(event);
        if (recipientIds.length === 0) return;

        const draft = this.buildMessage(event);
        await this.persistAndSend(recipientIds, draft);
      }

      /** Operação primária 1: quem deve receber o aviso. */
      protected abstract resolveRecipients(event: E): Promise<string[]>;

      /** Operação primária 2: o conteúdo do aviso. */
      protected abstract buildMessage(event: E): NotificationDraft;

      /** Passo comum: salva e empurra para o navegador de cada destinatário. */
      private async persistAndSend(
        recipientIds: string[],
        draft: NotificationDraft,
      ): Promise<void> {
        const unique = [...new Set(recipientIds)];
        const created: Notification[] = unique.map((id) =>
          createNotification(id, draft),
        );

        await Promise.all(created.map((n) => this.notifications.save(n)));
        await Promise.all(created.map((n) => this.channel.push(n.recipientId, n)));
      }
    }
    ```

    **Explicação:** essa é a classe que concentra o Template Method. O `handle()` funciona como uma receita: primeiro descobre quem vai receber (`resolveRecipients`), depois monta o texto (`buildMessage`) e no fim salva e envia tudo (`persistAndSend`). As duas primeiras etapas são `abstract` porque são justamente as partes que cada handler vai personalizar — no diagrama são aquelas operações marcadas com `#`. A última ficou `private` de propósito, para que nenhuma subclasse mexa na parte que é igual para todo mundo. E tem um detalhe interessante: a classe também implementa `EventHandler`, então ela está nos dois padrões ao mesmo tempo. É a AbstractClass do Template Method, mas também é um Observer que o EventBus sabe chamar — é nesse ponto que os dois padrões do diagrama se encontram.

    **Trecho 4 · `NewPostHandler` — ConcreteClass (avisa os seguidores)**<br>
    Arquivo: `src/modules/notifications/application/handlers/NewPostHandler.ts` — caixa do diagrama: **"NovoPostHandler — PostAprovado → seguidores"**.

    ```typescript
    /** PostAprovado → avisa os seguidores da comunidade. */
    export class NewPostHandler extends NotificationHandler<PostApprovedEvent> {
      readonly eventType = PostApprovedEvent.TYPE;

      constructor(
        notifications: NotificationRepository,
        channel: WebChannel,
        private readonly followers: FollowersRepository,
      ) {
        super(notifications, channel);
      }

      protected async resolveRecipients(event: PostApprovedEvent) {
        const ids = await this.followers.findFollowerIds(event.communityId);
        // o autor já recebe o aviso de aprovação; não duplicar
        return ids.filter((id) => id !== event.authorId);
      }

      protected buildMessage(event: PostApprovedEvent): NotificationDraft {
        return {
          type: "NEW_POST_IN_COMMUNITY",
          message: `Nova publicação em ${event.communityName}: ${event.postTitle}`,
          link: `/posts/${event.postId}`,
        };
      }
    }
    ```

    **Explicação:** um dos ConcreteClasses do diagrama (aquela flecha tracejada `extends`). Como herda de `NotificationHandler`, a classe não repete a receita inteira; ela só responde às duas perguntas que variam. Para decidir quem recebe, consulta o repositório de seguidores da comunidade e ainda tira o autor da lista, porque o autor já vai ser avisado pelo `ApprovedHandler` — assim ninguém recebe a mesma notícia em dobro. O outro método é só a montagem do texto da notificação.

    **Trecho 5 · `RejectedHandler` — ConcreteClass (avisa o autor, com motivo)**<br>
    Arquivo: `src/modules/notifications/application/handlers/RejectedHandler.ts` — caixa do diagrama: **"ReprovadoHandler — PostReprovado → autor"**.

    ```typescript
    /** PostReprovado → avisa o autor, com o motivo. */
    export class RejectedHandler extends NotificationHandler<PostRejectedEvent> {
      readonly eventType = PostRejectedEvent.TYPE;

      protected async resolveRecipients(event: PostRejectedEvent) {
        return [event.authorId];
      }

      protected buildMessage(event: PostRejectedEvent): NotificationDraft {
        return {
          type: "POST_REJECTED",
          message: `Sua publicação "${event.postTitle}" foi reprovada. Motivo: ${event.reason}`,
          link: `/posts/${event.postId}/edit`,
        };
      }
    }
    ```

    **Explicação:** essa é a versão mais enxuta de todas, e serve bem para mostrar que o padrão não exige estrutura pesada. Como o aviso vai só para o autor, a classe nem precisa de construtor próprio. O `eventType = PostRejectedEvent.TYPE` é o que separa os caminhos: o `EventBus` só entrega esse evento para quem se inscreveu nele. Vale comparar com o `ApprovedHandler`, que tem exatamente a mesma forma — muda só o tipo do evento e o texto que ele monta. É o mesmo esqueleto com conteúdos diferentes, e é justamente isso que evita código repetido.

    **Trecho 6 · `ModerationService` — o módulo externo que publica**<br>
    Arquivo: `src/modules/moderation/ModerationService.ts` — caixa do diagrama: **"ModeracaoService — módulo externo"** (flecha sólida para o `EventBus`).

    ```typescript
    /**
     * Só conhece o EventBus (Subject). Não importa nada de handlers,
     * canal web ou repositório de notificações.
     */
    export class ModerationService {
      constructor(
        private readonly posts: InMemoryPostRepository,
        private readonly bus: EventBus,
      ) {}

      async approve(postId: string) {
        const post = await this.requirePending(postId);
        await this.posts.save({ ...post, status: "APPROVED" });
        await this.bus.publish(
          new PostApprovedEvent(
            post.id,
            post.title,
            post.authorId,
            post.communityId,
            post.communityName,
          ),
        );
      }

      async reject(postId: string, reason: string) {
        const post = await this.requirePending(postId);
        await this.posts.save({ ...post, status: "REJECTED" });
        await this.bus.publish(
          new PostRejectedEvent(post.id, post.title, post.authorId, reason),
        );
      }
    }
    ```

    **Explicação:** essa é a caixa "módulo externo" do diagrama, e é aqui que dá para enxergar melhor o desacoplamento do Observer. O construtor recebe só duas coisas: o repositório de posts e o bus. Não tem nenhuma referência a handler, a repositório de notificação ou a canal web — quem publica não sabe e nem precisa saber quem está escutando. Quando o moderador chama `approve()` ou `reject()`, o serviço salva a decisão e publica um evento, o `PostApprovedEvent` ou o `PostRejectedEvent`. Esses eventos são as caixas bege lá embaixo do diagrama: objetos imutáveis que já nascem com todos os dados que os handlers vão precisar (id e título do post, autor, comunidade e, na reprovação, o motivo). Como os dados chegam todos dentro do próprio evento, o módulo de notificação não precisa conhecer o módulo de posts. Uma observação: o trecho deixa de fora o `requirePending()`, que é a verificação que impede moderar duas vezes o mesmo post, e a `InMemoryPostRepository` — os dois estão no arquivo original.

    **Trecho 7 · `buildContainer()` — a fiação (quem inscreve quem)**<br>
    Arquivo: `src/lib/container.ts` — não é uma caixa do diagrama, mas é onde as inscrições `subscribe` do Subject acontecem.

    ```typescript
    /**
     * ÚNICO lugar que conhece todas as classes concretas:
     * monta o grafo de dependências e inscreve os Observers no Subject.
     */
    export function buildContainer() {
      const notifications = new InMemoryNotificationRepository();
      const followers = new InMemoryFollowersRepository({
        tech: ["ana", "bruno", "carla"],
        games: ["bruno"],
      });
      const channel = new SseWebChannel();

      const bus = new EventBus();
      bus.subscribe(new NewPostHandler(notifications, channel, followers));
      bus.subscribe(new ApprovedHandler(notifications, channel));
      bus.subscribe(new RejectedHandler(notifications, channel));

      const posts = new InMemoryPostRepository([
        { id: "p1", title: "Novo framework lançado", authorId: "ana", communityId: "tech", communityName: "Tecnologia", status: "PENDING" },
        { id: "p2", title: "Review do jogo do ano", authorId: "ana", communityId: "games", communityName: "Games", status: "PENDING" },
      ]);
      const moderation = new ModerationService(posts, bus);

      return { bus, notifications, channel, moderation };
    }
    ```

    **Explicação:** por fim, algo que não aparece como caixa no diagrama, mas que é o que faz tudo funcionar: a fiação. O `buildContainer()` é o único lugar do código que conhece todas as classes concretas. As três linhas `bus.subscribe(...)` são o elo entre cada handler e o bus: `NewPostHandler` e `ApprovedHandler` escutam `PostApproved`, enquanto `RejectedHandler` escuta `PostRejected`. Depois disso, o `ModerationService` já nasce com o bus na mão e o ciclo se fecha. As portas `NotificationRepository`, `FollowersRepository` e `WebChannel` também são ligadas aqui às suas versões em memória (`InMemory*` e `SseWebChannel`), então trocar tudo por um banco de dados mais para frente não mexeria em nenhum handler.

    **Como provar que está tudo funcionando:** o jeito mais direto é rodar os testes: `cd demonstracao_codigos && npm test`. São cinco testes (`node:test` + `tsx`) e todos passam — 5 pass, 0 fail. Eles cobrem exatamente o que foi dito aqui: dois handlers reagindo ao mesmo evento, separação por tipo de evento, entrega pela canal web, uma falha isolada dentro do `publish` e a proteção contra moderação duplicada.
